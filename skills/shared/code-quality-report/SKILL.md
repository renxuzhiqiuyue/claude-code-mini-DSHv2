# 代码与项目质量报告 Skill

你具备撰写**代码质量**与**项目质量** Markdown 报告的能力。报告对象是当前仓库的源码、结构与工程实践，**不是**进度汇报、业务调研或运维故障复盘。

可与 `load_skill("code-review")` 配合：先审查代码，再用本 skill 整理成结构化质量报告。

## 何时使用

- 用户要求「代码质量报告」「项目质量评估」「技术债报告」「健康度检查」
- 完成 `code-review` 或静态分析后，需要将发现**汇总为可交付 .md**
- 需要评估：测试、架构、依赖、文档、可维护性、安全与规范遵守情况

## 不适用

- 项目进度 / 周报 / 排期
- 业务需求调研、产品方案
- 生产故障复盘（除非焦点是**代码/工程根因**）

## 执行流程

### 1. 划定范围

向用户确认（若未说明）：

| 项 | 示例 |
|----|------|
| 范围 | 全仓 / 指定目录 / 某模块 / 某 PR 变更 |
| 深度 | 快速扫描 / 标准评估 / 深度审计 |
| 输出路径 | `docs/quality/YYYY-MM-DD-<项目名>.md` |

### 2. 收集证据（必须基于仓库事实）

```bash
# 结构概览
find . -type f -name "*.py" | head -50   # 按语言调整
glob **/*.{py,ts,go}

# 测试与覆盖率（有则运行）
pytest --co -q 2>/dev/null || true
npm test 2>/dev/null || true

# 依赖与安全（按栈选用）
pip-audit / npm audit / cargo audit

# 重复与体量
wc -l $(find src -name "*.py" 2>/dev/null)
grep -r "TODO\|FIXME\|HACK" --include="*.*" .
grep -r "except:" --include="*.py" .   # 示例：宽泛异常
```

- 用 `read_file`、`bash` 读取**真实文件**与命令输出（本环境无 `glob` 工具，列目录用 `bash ls`）
- 每条问题须指向**具体路径**（及行号，若已知）
- 不编造覆盖率数字、未运行的 audit 结果

### 3. 评估维度

#### 代码质量

| 维度 | 检查要点 |
|------|----------|
| 正确性 | 边界条件、错误处理、并发与资源释放 |
| 可读性 | 命名、函数长度、嵌套深度、注释是否解释「为什么」 |
| 一致性 | 风格、目录约定、重复逻辑 |
| 类型与安全 | 类型标注、注入/密钥/敏感信息、依赖 CVE |
| 测试 | 单测/集成测是否存在、关键路径是否覆盖 |

#### 项目质量

| 维度 | 检查要点 |
|------|----------|
| 架构 | 模块边界、耦合、分层是否清晰 |
| 文档 | README、API 说明、关键设计是否缺失或过时 |
| 工程化 | CI、lint、格式化、pre-commit 是否配置 |
| 依赖 | 版本锁定、过时包、传递依赖风险 |
| 可维护性 | 技术债密度、TODO/FIXME、大文件/上帝类 |
| 可观测性 | 日志、错误码、调试友好度（如适用） |

为每个维度给出 **评级**（见下方模板）和**证据**。

### 4. 撰写与落盘

- 使用下方主模板，按需增删章节
- `write_file` 写入约定路径
- 文末附**问题清单**（带优先级 P0–P2）
- 向用户返回路径 + 3 句摘要（最严重问题 + 优先改进项）

## 格式规范

1. **结论先行**：摘要与评分表放在前面
2. **证据绑定**：每个问题必须有 `路径` 或命令/测试输出依据
3. **优先级**：P0 安全/正确性/数据丢失 · P1 可维护性/缺测 · P2 风格/文档
4. **代码引用**：短片段用 fenced block；长文件只引关键行
5. **客观表述**：「未找到单测」而非「测试很差」；有数据写数据
6. **篇幅**：标准报告 1500–3000 字；深度审计可更长，用附录承载明细

### 禁止事项

- 不编造覆盖率、audit 结果、未读文件的结论
- 不写成进度周报、业务报告或运维复盘
- 不堆砌无结论的代码粘贴
- 不未经确认覆盖已有质量基线文档
